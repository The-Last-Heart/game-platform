# LH-006 — Versioned Game Content and Release Platform

Day: 1 PM
Depends on: completed platform/realtime/admin foundations; LH-005 may proceed earlier
Commit: feat(content): add versioned game content releases

## Product outcome

The game no longer grows through hardcoded levels or mutable production settings. Authorized operators can create validated content candidates and immutable releases; every new match pins the exact challenge, translation, rule, and power versions it will use.

## Operator journeys

1. Create a wait-for-state variant, validate it, approve it, and publish a catalog.
2. Start a new match and prove it uses the published parameters without a mobile rebuild.
3. Publish a later catalog and prove the active match remains unchanged.
4. Pause a defective variant for future selections.
5. Roll back by creating a new release from a previous approved version.
6. Reject an invalid or incompatible catalog before it reaches players.

## Core content model

Create durable, versioned product concepts for:

- Challenge family capability.
- Challenge category.
- Challenge template/variant.
- Immutable template version.
- Localized challenge copy and failure reasons.
- Challenge catalog and immutable catalog release.
- Game-mode rule release.
- Power configuration release.
- Mobile localization catalog release.
- Daily-goal definition and later release.
- Asset identity and compatibility metadata.

Existing wait-for-state content must be migrated into this model and shipped in a valid bootstrap release.

## Challenge definition requirements

Every published definition declares:

- Stable identity, internal title, owner, family, category, and difficulty.
- Arabic instruction, optional hint, and localized outcome reasons.
- Intro, future start, active, and result durations.
- Allowed/prohibited inputs and authoritative success/failure rules.
- Heart consequence, energy reward, and performance measure.
- Family-specific parameters.
- Device capabilities and accessibility alternative.
- Eligible modes and round ranges.
- Selection weight and repetition cooldown.
- Minimum app version and required assets.

Unknown, contradictory, unsafe, unsupported, or incomplete fields must be rejected.

## Lifecycle and governance

- Draft is editable.
- Submission freezes a review candidate.
- Approval records reviewer, timestamp, validation, notes, and change summary.
- Publish creates immutable releases and changelogs.
- Release can be immediate or scheduled.
- Pause affects future selection without rewriting active matches.
- Rollback creates new history; it never rewrites published history.
- Retired content remains available for historical match investigation.
- Publishing, pause, resume, rollback, retire, and scheduling are permissioned and audited.

## Catalog composition

The release model must support:

- Eligible challenges per mode.
- Difficulty curve by round band.
- Relative weights.
- Per-family/per-template repeat cooldown.
- Limits for sensor, audio, pair, and risk challenges per match.
- Capability and accessibility coverage.
- App-version compatibility.
- Emergency exclusions.

A catalog cannot publish unless it can produce a complete fair match for every supported capability profile.

## Match pinning and deterministic use

At match creation, pin:

- Game-mode rule release.
- Challenge catalog release.
- Localization release.
- Power configuration release.

Persist pins in match history and expose them in safe admin/support views. Reconnect, replay, and investigation must recover the same definitions. Selection must be deterministic enough to investigate and must respect weights, cooldowns, compatibility, and fairness rules.

## Emergency controls

Implement actual product behavior for:

- Pause a challenge from future selection.
- Disable a challenge family for unsupported app versions.
- Pause new matchmaking.
- Enable/disable public bot fill and set its wait threshold.
- Disable new offensive power activation.

Controls require permission, reason, confirmation, effective time, and audit entry. No control may secretly rewrite hearts, accepted results, or active match releases.

## Minimal administration surface

Provide a functional, permissioned management surface sufficient to exercise the lifecycle. It may be visually completed in LH-010, but it cannot be a raw database-only feature or a dead menu item.

## Out of scope

- Full Studio visual editor and device playtest.
- Additional challenge engines.
- Arbitrary executable challenge scripts.
- Mutation of active matches.

## Acceptance criteria

- Existing wait-for-state is served from a published definition.
- Editing an approved version is impossible; a new draft/version is required.
- Next match uses a newly published parameter; active match keeps prior pins.
- Invalid durations, rewards, missing Arabic, unknown parameters, missing fallback, and unsupported app versions are rejected.
- Pause and rollback behavior is observable and audited.
- Match history exposes all four release identifiers without secrets.
- Concurrent publish attempts cannot create ambiguous current releases.
- Migrations run once and skip safely on the second run.
- Contracts are shared by backend/admin/mobile; no divergent handwritten copies.
- Existing gameplay and admin regression checks remain green.

## Required evidence

- Before/after challenge parameter demonstrated in two new matches.
- Active-match pin stability demonstrated across a publish.
- Invalid publish rejection samples.
- Pause and rollback audit history.
- Migration run twice.
- Commit hash and clean tree.
