# LH-014 — Final RC1 Acceptance and Handoff

Day: 5 PM
Depends on: LH-005 through LH-013
Commit: fix(release): close rc1 acceptance defects

## Product outcome

RC1 is accepted through observed business journeys, not by test count or implementation claims. This milestone adds no new feature scope. It reproduces and fixes release-blocking defects, repeats the full gate, packages evidence, and leaves one clean local commit.

## Severity gate

- P0: data loss, security exposure, wrong winner/hearts, unusable release, or broad outage. Zero allowed.
- P1: core journey failure, unfair result, reconnect corruption, inaccessible required path, broken admin control, or missing audit. Zero allowed.
- P2: significant but recoverable defect. Must be fixed or explicitly rejected by Product Owner with rationale before RC.
- P3: cosmetic/minor defect. May enter a documented post-RC list only when it does not violate the reference or accessibility acceptance.

## Fourteen business acceptance journeys

### 1. First-time player

Launch, Arabic onboarding, identity, home, Quick Survival, six accepted seats, full match, winner summary, and rematch.

### 2. Returning/private group

Skip completed onboarding, create room, share code, join six distinct players, one ready countdown, full match, and party rematch.

### 3. Training

Choose every eligible engine, understand the action, practice, receive exact feedback, retry, and confirm no competitive reward/analytics pollution.

### 4. Hearts

Start with three, apply exactly one loss per failed challenge, reach zero, become spectator, reject competitive input, and continue observing the winner.

### 5. Core challenge catalog

Run all eleven published families with success, failure, timeout, exact-deadline, late, duplicate, reconnect, capability fallback, and result explanation as applicable.

### 6. Energy

Four standard successes fill the meter, grant one power once, preserve inventory through reconnect, and explain full inventory.

### 7. Attack and defense

Danger Pulse target selection, ordinary defense, Shield, Reflection, sender defense, protection, illegal target, expiration, elimination, and return to next challenge.

### 8. Timing fairness

Early, valid, exact-deadline, late, duplicate, retry, simultaneous resolution, pair boundary, and deterministic tie behavior.

### 9. Reconnect

Resume during queue, lobby, countdown, every engine category, result, power states, spectator, completed match, and rematch. Confirm one lease owner and no reset deadline.

### 10. Content lifecycle

Create, validate, preview, playtest, submit, review, approve, schedule/publish, start pinned match, pause, resume, rollback, retire, and inspect history.

### 11. Accessibility

Complete a full eligible catalog with no-motion/no-audio needs, reduced motion, equivalent cues, pair fallback, and private eligibility.

### 12. Live incident and support

Detect an unhealthy challenge/match, investigate timeline, pause future selection or halt only the affected match, support/search a player, apply/remove suspension, and inspect audit.

### 13. Admin language and permissions

Exercise every route and action in EN/LTR and AR/RTL. Verify super_admin, content_manager, live_ops, translator, and viewer can do only their permitted work.

### 14. Fresh release

From documented inputs, configure a fresh environment, migrate twice safely, bootstrap twice safely, start backend/admin, install mobile release, complete health checks, play a smoke match, stop gracefully, and execute rollback procedure without secrets or data corruption.

## Full regression gate

Run and observe:

- Repository diff/format/secrets checks.
- Workspace and contracts verification.
- Backend format, lint, unit, integration, end-to-end, open-handle, and production build.
- Admin format, lint, unit/component/integration, browser journeys, and production build.
- Mobile format, analyze, unit/widget/integration, device journeys, and release builds.
- Database migration/bootstrap idempotency.
- Redis/database dependency and recovery checks.
- Six-client playable/full-match/power/reconnect simulations.
- Product analytics reconciliation.
- Dependency/security audits.
- Container/deployment smoke tests where supported.

Do not use force exit, disabled checks, ignored warnings, fake fixtures presented as production analytics, or screenshots of mocked behavior as acceptance.

## Defect closure

- Reproduce every blocker before changing it.
- Fix only release defects; no new module or product idea.
- Add regression coverage.
- Re-run the affected journey and full gate.
- Document genuine external non-executable checks precisely.

## Final commit policy

Create the milestone commit only after all RC defects are closed and the full gate passes. The commit includes only LH-014 fixes/evidence/doc updates. Confirm an empty working tree.

Do not push, rebase, reset, clean, stash, switch branches, or rewrite history.

10. Exact test/build/simulation/migration/audit results.

12. P0/P1/P2/P3 ledger.
13. External blockers and their owners.
14. Final git status.
15. Confirmation of local commits and no push/history rewrite.

## Acceptance criteria

- All fourteen business journeys pass with observed evidence.
- Zero P0 and P1 defects remain.
- No P2 remains without explicit Product Owner rejection of release or written acceptance.
- Full regression gate passes without forced exits, disabled checks, fake data, or hidden warnings.
- Release artifacts and external-blocker ledger are complete.
- Documentation matches the behavior that was actually observed.
- Final local commit exists and the working tree is clean.

## Required evidence

- One indexed evidence manifest linking every journey to logs, screenshots, recordings, test output, or artifact hashes.
- Complete commit list with full hashes.
- Exact regression command/results table.
- Release artifact inventory.
- Defect and external-blocker ledgers.
- Final git status.

## Completion rule

LH-014 ends the five-day roadmap. Do not begin post-RC features. Preserve the clean committed state for Product Owner review.

## Acceptance decision

The final report must conclude with exactly one:

- RC1 accepted for controlled release.
- RC1 blocked.

If blocked, identify the failed journey, severity, reproduction, responsible milestone, and next exact correction. Do not soften or hide the blocker.
